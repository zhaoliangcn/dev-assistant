# ADR-001: 定时任务功能架构设计

## 背景

需要实现一个通用的定时任务功能，支持在指定时间或按周期执行用户定义的任务逻辑。

## 需求

- 支持 cron 表达式调度
- 支持固定间隔调度（如每 30 秒）
- 支持一次性延迟任务
- 支持任务 CRUD 管理
- 支持任务执行记录和状态追踪
- 支持失败重试
- 支持分布式部署（无单点故障）
- 支持动态注册/取消任务

## 架构决策

### 决策 1: 调度器与执行器分离

**方案**：将调度引擎（Scheduler）和任务执行器（Executor）拆分为两个独立模块。

**理由**：
- 调度器负责时间计算和任务触发，执行器负责实际业务逻辑，职责单一
- 两者可以独立扩缩容，调度器无状态可水平扩展
- 执行器可以按业务类型分组，实现任务隔离

### 决策 2: 基于数据库轮询 + 内存时间轮的混合调度策略

**方案**：使用数据库作为任务持久化存储，调度器定期轮询即将到期的任务，同时使用内存中的时间轮（Timing Wheel）进行高精度触发。

**理由**：
- 纯数据库轮询（如每秒扫表）在任务数量大时性能差
- 纯内存调度（如 Quartz 的 RAMJobStore）不支持持久化和故障恢复
- 混合策略：数据库轮询获取"最近 N 秒内到期"的任务加载到内存时间轮，由时间轮精确触发
- 兼顾了持久化可靠性和触发精度

### 决策 3: 任务执行结果通过事件总线异步处理

**方案**：执行器完成任务后，将执行结果发布到事件总线（Event Bus），由结果处理器异步更新任务状态和记录。

**理由**：
- 避免执行器阻塞等待存储写入
- 支持下游订阅执行事件（如告警、通知）
- 便于扩展（如日志采集、指标监控）

### 决策 4: 使用乐观锁保障任务不被重复调度

**方案**：任务记录中维护 `version` 字段，调度器在获取任务执行权时使用 `CAS (Compare-And-Swap)` 方式更新状态。

**理由**：
- 分布式环境下多个调度器实例可能同时扫描到同一任务
- 乐观锁比分布式锁（如 Redis 锁）更轻量，无额外依赖
- 配合 `scheduled_at` 时间窗口，可有效防止重复调度

### 决策 5: 任务定义采用插件化设计

**方案**：定义 `TaskHandler` 接口，业务方实现该接口注册到系统。任务配置中通过 `handler_id` 关联具体实现。

**理由**：
- 业务逻辑与调度框架解耦
- 新增任务类型无需修改核心代码
- 便于单元测试和 Mock

## 非功能性设计

- 调度精度：秒级（±1s）
- 任务容量：单实例支持 10,000+ 个活跃任务
- 高可用：多实例部署，通过数据库乐观锁竞争
- 可观测：Prometheus 指标 + 执行日志

## 备选方案

- **方案 A（纯 Redis 延迟队列）**：依赖 Redis 的有序集合（ZSet）实现，但缺少持久化保证和复杂调度能力。
- **方案 B（Quartz 框架）**：功能完善但较重，与 Spring 强耦合，集群模式下依赖数据库锁。
- **方案 C（Kafka 时间轮）**：适合高吞吐场景，但引入 Kafka 增加了系统复杂度。
